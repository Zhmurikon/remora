# Операции с секретами и служебными ролями

## Ключи приложения

Секреты передаются только через env-файлы с правами `0600` или менеджер секретов. В логах,
резервных копиях исходников и задачах CI их быть не должно. В staging/production приложение
не запускается с локальными значениями `SECRET_KEY`, S3 и Meilisearch, без
`DATA_ENCRYPTION_KEYS` или с небезопасной cookie.

`SECRET_KEY` — текущий ключ подписи JWT. При ротации сначала добавить прежний ключ в
`JWT_PREVIOUS_SECRET_KEYS` (JSON-массив), установить новый `SECRET_KEY` и перезапустить все
API/worker. Новые JWT получают `kid`, старые принимаются до истечения максимального TTL.
После этого прежний ключ удалить из массива. Refresh-, API- и одноразовые токены в БД хранятся
только как SHA-256/Argon2-хэши и отдельной расшифровки не требуют.

`TRANSCRIBER_SERVICE_TOKEN` аутентифицирует Next.js перед внутренним API расшифровки,
`TRANSCRIBER_ACCESS_SECRET` подписывает закрытую браузерную cookie. Они независимы друг от
друга, от пользовательского кода доступа и от `SECRET_KEY`.

`DATA_ENCRYPTION_KEYS` — JSON-массив base64url-ключей AES-256-GCM, новый ключ всегда первый.
Зашифрованная запись содержит версию и `kid`; дополнительные ключи нужны только для чтения
старых записей. Ротация: добавить новый ключ первым, фоново перешифровать записи, убедиться,
что старый `kid` больше не встречается, затем удалить старый ключ. Контекст записи передаётся
как AAD, поэтому ciphertext нельзя переставить между пользователями или назначениями.

Новый ключ можно получить командой `openssl rand -base64 32 | tr '+/' '-_'` и хранить без
переносов строки. Фактические значения в документацию не записываются.

## PostgreSQL

В production используются три независимых логина:

- `remora_migrator` владеет схемой и применяется только одноразовой задачей миграции;
- `remora_runtime` имеет DML-доступ без DDL и используется API/worker;
- `remora_readonly` предназначен для диагностики и отчётов.

Шаблон `deploy/security/postgres-roles.sql` запускается администратором на новой БД с тремя
паролями через параметры `psql -v`. Пароли не передают в аргументах на общей машине: там
используют временный файл переменных или менеджер секретов. После выдачи прав проверить
`\du`, `\dp` и отказ `CREATE TABLE` под runtime-пользователем. Миграционный пароль не должен
попадать в контейнеры API и worker.

## S3/MinIO

Root-ключ используется только при первичной настройке. Приложению создаётся отдельный
пользователь с политикой `deploy/security/minio-app-policy.json`: только list/get/put/delete
в `remora-media` и `remora-audio`, без управления пользователями, политиками и другими
бакетами. Бакеты остаются приватными; доступ браузера — только по короткоживущей подписи.

После ротации S3-ключа сначала выпустить второй прикладной ключ, переключить API/worker,
проверить загрузку и чтение, затем отозвать прежний. Root-ключ не хранится в `.env` приложения.

## Проверка ротации

После каждой ротации проверить вход, обновление сессии, письмо подтверждения/сброса, загрузку
и чтение изображения, TTS, полный экспорт, worker и отсутствие секретов в структурных логах.
Событие и дату ротации записать во внешний журнал эксплуатации без значений ключей.
