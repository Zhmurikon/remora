# Remora — план разработки

Расчёт: один разработчик + Claude Code, полный рабочий день. Оценки в неделях — с запасом на отладку, но без запаса на болезни и отпуска. Итого до публичного запуска — **25–31 неделя** при полном объёме. Ниже указано, что можно сократить.

**Принцип нарезки:** каждый этап заканчивается работающим состоянием продукта, которое можно показать живому человеку. Никаких этапов вида «пишем половину бэкенда».

**Критические точки, после которых можно останавливаться и смотреть на реальность:**

- После E5 — продукт полноценно решает задачу одного человека. Можно давать друзьям.
- После E7 — можно запускать закрытую бету и мерить удержание.
- После E9 — можно брать деньги.
- E8 (классы) — единственный крупный блок, который допустимо перенести за релиз, если время поджимает.

## E0. Фундамент проекта — 1 неделя

**Дополнение 16.09.2026:** по отдельному запросу до завершения E6 реализован агентский срез:
персональные API-токены, JSON API приватных наборов и полной структуры курсов, stdio MCP
и навык создания материалов из источников. Это не встроенная ИИ-генерация E13+ и не полный
визуальный редактор E6B. После реализации E6B агентский срез расширен отдельной структурой,
копированием и явным удалением статей/разделов; MCP содержит 15 инструментов.
Контракт и подключение: [07-agent-api.md](07-agent-api.md).

**Цель:** решения зафиксированы, окружение поднимается одной командой, первый коммит проходит CI.

**Задачи**

1. Инициализация монорепо: pnpm workspaces, структура `apps/` + `packages/`, единые tsconfig/eslint/prettier.
2. `apps/api`: FastAPI, Poetry/uv, ruff + mypy, структура слоёв (`routers` / `services` / `repositories` / `models` / `schemas`).
3. `docker-compose.yml` для разработки: postgres, redis, meilisearch, mailhog, minio (локальная замена S3).
4. Alembic, первая миграция, соглашения по именованию.
5. Каркас `apps/web` (Next.js App Router) и `apps/app` (Vite + React + TS).
6. `packages/ui`: Tailwind-пресет, токены дизайн-системы (цвет, типографика, отступы, радиусы), базовые компоненты — Button, Input, Card, Modal, Toast.
7. `packages/api-client`: генерация TS-клиента из OpenAPI (openapi-typescript + скрипт `pnpm gen:api`).
8. CI: линт, типы, тесты, сборка образов.
9. `CLAUDE.md` в корне: правила проекта, соглашения, команды, чтобы агент не переизобретал стиль каждую сессию.
10. Регистрация домена, выбор облачного провайдера, создание S3-бакета и почтового отправителя.

**Definition of Done**

- `docker compose up` поднимает всё окружение с нуля на чистой машине.
- `/api/v1/health` отвечает, оба фронта открываются и рендерят страницу с компонентом из `packages/ui`.
- CI зелёный на пустом проекте.

**Ловушки:** не увлекаться дизайн-системой. Нужно 8–10 компонентов, остальное — по мере надобности.

## E1. Скелет платформы и аутентификация — 2.5 недели

**Цель:** пользователь регистрируется, входит любым способом, попадает в пустой кабинет.

**Задачи**

_Бэкенд_

1. Модели `users`, `user_settings`, `oauth_accounts`, `refresh_tokens`, `consents`; миграции.
2. Пароли: argon2id, политика, проверка по словарю утечек.
3. JWT-слой: access 15 мин, refresh в httpOnly cookie, ротация с детекцией переиспользования (при повторном использовании — отзыв всей семьи токенов).
4. Регистрация + подтверждение email (одноразовые токены, срок жизни, письмо через SMTP-провайдера).
5. Восстановление пароля.
6. OAuth: VK ID, Яндекс ID — стандартный authorization code flow; Telegram Login Widget — проверка подписи по HMAC от bot token.
7. Логика связывания аккаунтов: один email — один пользователь, несколько провайдеров.
8. Rate limiting (Redis, sliding window) на login, register, password-reset, oauth-callback.
9. Управление сессиями: список устройств, отзыв.
10. Возрастной гейт: сбор даты рождения, флаг `requires_guardian_consent` (сама процедура согласия — в E10).
11. Единый формат ошибок API, middleware с request_id, структурные логи.

_Фронтенд_

12. `apps/web`: страницы входа/регистрации/восстановления, кнопки соцвхода, обработка колбэков, редирект в SPA после успеха.
13. `apps/app`: оболочка приложения — роутинг, защищённые маршруты, layout с навигацией, автообновление токена (single-flight refresh, чтобы 10 параллельных 401 не устроили 10 рефрешей).
14. Пустой кабинет с онбординг-заглушкой.
15. Страница настроек: профиль, смена пароля, привязанные аккаунты, сессии.

**DoD**

- Регистрация всеми четырьмя способами работает end-to-end на стейджинге.
- Тесты: жизненный цикл токенов, ротация, попытка переиспользования, rate limiting, связывание аккаунтов.
- Ручная проверка: закрыл вкладку → вернулся через день → всё ещё авторизован.

**Ловушки:** OAuth-провайдеры требуют верифицированного домена и заполненных карточек приложений — подать заявки в начале этапа, не в конце. У VK ID модерация приложения занимает время.

## E2. Наборы, карточки, редактор, медиа — 3 недели

**Цель:** можно создать набор с богатым содержимым и увидеть его.

**Задачи**

_Бэкенд_

1. Модели `folders`, `study_sets`, `cards`, `card_stars`, `media_assets`, `subjects`, `tags`; миграции и индексы.
2. CRUD наборов с проверкой прав, мягкое удаление, дублирование набора.
3. Батчевые операции с карточками: создание/обновление/удаление списком, изменение порядка одним запросом.
4. Санитизация текста: whitelist-подход к разметке, защита от XSS, ограничение длины полей.
5. Валидация LaTeX на сервере (KaTeX через node-сервис или python-обёртка) — битые формулы не должны сохраняться молча.
6. Медиа-пайплайн: presigned URL → загрузка в S3 → фоновая задача (проверка mime по сигнатуре, очистка EXIF, конвертация в WebP/AVIF, три размера, checksum, дедупликация) → обновление статуса.
7. Квоты на загрузку и размер (задел под тарифы).
8. Справочник предметов: наполнение начальным деревом (школьные предметы, языки, вузовские направления).

_Фронтенд_

9. Библиотека: список наборов, папки, drag-and-drop, фильтры, поиск по своему.
10. Редактор набора:
    - построчное редактирование двух сторон с автосохранением и индикатором состояния;
    - режим массового ввода: textarea + выбор разделителей + живой предпросмотр таблицы распознанных карточек;
    - drag-and-drop порядка карточек, дублирование, удаление с отменой;
    - загрузка изображений с превью и прогрессом;
    - переключение типа содержимого: текст / формула / код, с живым рендером;
    - поля транскрипции и альтернативных ответов (сворачиваемые, чтобы не пугать интерфейсом).
11. Страница набора внутри SPA: обзор, список карточек, кнопки режимов (пока неактивные), настройки видимости.
12. Рендер контента: общий компонент в `packages/ui`, умеющий текст + KaTeX + код + изображение. Используется и в редакторе, и в тренировках, и на публичном сайте.

**DoD**

- Набор на 100 карточек с картинками, формулами и кодом создаётся, сохраняется, корректно отображается на всех трёх поверхностях.
- Массовый ввод переваривает реальный экспорт из Quizlet, вставленный из буфера.
- Автосохранение не теряет данные при обрыве сети (проверить искусственно).

**Ловушки:** редактор — самый недооцениваемый по трудоёмкости экран. Заложить на него больше половины этапа.

## E3. Движок обучения: FSRS, Карточки, Заучивание — 3.5 недели

**Цель:** главная ценность продукта работает. Человек может реально выучить набор.

**Задачи**

_Ядро_

1. Интеграция `py-fsrs`: обёртка-сервис `SchedulerService` с фиксированной версией параметров, версионирование схемы состояний.
2. Модели `card_states`, `reviews`, `study_sessions`, `user_set_progress`; индексы под выборку очереди.
3. Инициализация состояний: ленивая — состояние создаётся при первом показе карточки, не при создании набора (иначе 10 млн пустых строк).
4. Раздельные состояния по направлению (термин→определение / обратно).
5. Сервис очереди: просроченные повторения + новые в пределах дневного лимита + перемешивание с учётом того, чтобы связанные карточки не шли подряд.
6. Приём ответов батчем, идемпотентность по `client_review_id`, пересчёт состояния, запись в журнал.
7. Настройки пользователя: целевое удержание, лимиты новых и повторений в день, максимальный интервал.
8. Прогноз нагрузки: сколько карточек к повторению в ближайшие 14 дней.
9. `packages/core`: TS-порт функции предпросмотра интервалов (показать пользователю «через 3 дня / через 10 дней» на кнопках), с тестом на соответствие серверному расчёту.

_Режимы_ 10. Единая оболочка тренировки: загрузка очереди, локальное состояние сессии (Zustand), очередь неотправленных ответов в localStorage с ретраями, экран прогресса, горячие клавиши, обработка выхода со страницы. 11. Режим «Карточки»: переворот, навигация, свайпы, автопроигрывание, перемешивание, фильтры, опциональная запись в FSRS. 12. Режим «Заучивание»: раунды по 7–10 карточек, прогрессия типов вопроса (выбор из 4 → ввод → свободное воспроизведение) в зависимости от стабильности, кнопки самооценки, разбор ошибок с подсветкой различий. 13. Генерация дистракторов для вопросов с выбором: из того же набора, с приоритетом семантически близких (на MVP — по длине и первым буквам, без ИИ), защита от дубликатов. 14. Экран результатов сессии: сколько пройдено, что улучшилось, когда следующее повторение, кнопка «продолжить». 15. Статистика набора: распределение по состояниям, процент освоения, проблемные карточки.

**DoD**

- Тесты планировщика: последовательности ответов дают ожидаемые интервалы, состояния переходят корректно, повторная отправка одного ответа ничего не ломает.
- Ручной прогон: набор на 50 карточек проходится за несколько сессий, интервалы растут, при ошибке карточка возвращается.
- Обрыв сети посреди сессии не теряет ни одного ответа.

**Ловушки:** соблазн реализовать «свой умный алгоритм». Не надо. FSRS — библиотека, её нужно правильно вызвать и правильно хранить состояние, а вся сложность в UX вокруг неё.

## E4. Тест, Письмо, Аудирование, TTS — 2.5 недели

**Задачи**

1. Режим «Тест»: конструктор (число вопросов, типы, направление, источник), генерация набора вопросов на сервере с фиксацией в `test_attempts`, прохождение, проверка, страница разбора, пересдача по ошибкам.
2. Печатная версия теста и листа ответов (серверная генерация PDF).
3. Нормализация и сравнение ответов (`packages/core` + зеркало на Python): регистр, пробелы, ё/е, пунктуация, артикли, диакритика, `alt_answers`, расстояние Левенштейна с порогом по длине, статус «опечатка».
4. Три уровня строгости проверки в настройках.
5. Режим «Письмо» поверх этой логики.
6. TTS-сервис: интеграция Яндекс SpeechKit, кэш `tts_cache` по sha256(текст+язык+голос+скорость), учёт символов в `usage_counters`, фоновая пакетная озвучка набора, выбор голоса.
7. Режим «Аудирование»: воспроизведение, скорость, повтор, ввод или выбор ответа, вариант «диктант».
8. Аудиоплеер в `packages/ui` с предзагрузкой следующей карточки (иначе пауза убивает ритм).
9. Печатные материалы набора: карточки для вырезания (2 раскладки), список терминов.

**DoD**

- Тесты нормализатора на 60+ реальных кейсах (включая русские и английские, с диакритикой и без).
- Стоимость TTS на одну карточку после прогрева кэша стремится к нулю (проверить по счётчику).
- Тест на 30 вопросов проходится и печатается.

**Сокращение при нехватке времени:** «Аудирование» и печатные материалы переносятся в E13.

## E5. Импорт и экспорт — 1.5 недели

**Цель:** снять главный барьер перехода — «у меня всё уже в Quizlet/Anki».

**Задачи**

1. Универсальный парсер текста: автодетект разделителей, предпросмотр, ручная корректировка, обработка кавычек и многострочных значений.
2. CSV/TSV с маппингом колонок в UI (термин, определение, транскрипция, подсказка, изображение по URL).
3. Anki `.apkg`: распаковка, чтение SQLite, извлечение заметок и полей, медиа-файлы из архива, приведение типов заметок к двум сторонам, отчёт о том, что упростилось.
4. Anki `.txt`.
5. Фоновая обработка больших файлов: задача, прогресс, построчный отчёт об ошибках, частичный импорт.
6. Мастер импорта с Quizlet: пошаговая инструкция со скриншотами (открыть набор → Экспорт → скопировать → вставить) прямо в интерфейсе. Это UX-задача, и она важнее технической части.
7. Экспорт набора: TXT с настраиваемыми разделителями, CSV, Anki-совместимый TXT, PDF.
8. Экспорт аккаунта целиком: фоновая задача, ZIP с JSON + медиа, ссылка на скачивание по почте, срок жизни ссылки.

**DoD**

- Импортированы и корректно отображаются: реальный экспорт Quizlet (RU и EN), реальный `.apkg` с медиа на 500+ карточек, CSV из Excel с кириллицей и BOM.
- Экспортированный из Remora файл импортируется обратно без потерь.

## E6. Публичный сайт, каталог, поиск, SEO — 3 недели

Уточнение после брифа: публичная единица — курс, категории заменены плоскими тегами.
E6A включает минимальную оболочку курса и каталог; полноценный редактор разделов и статей
вынесен в E6B. Актуальные решения: [бриф E6](06-courses-brief.md), задачи: `TODO.md`.
Согласованная главная реализована по [брифу](09-homepage.md) и `design.md`: упражнение
из пяти вопросов без регистрации, без сравнения с Quizlet и вымышленных показателей.
Это решение заменяет прежний пункт об отстройке от Quizlet на лендинге ниже.
Редакционный блог опубликован на дев-сервере: статический список и статьи с SEO, файловый
редакционный процесс описан в [документе](10-blog.md). Выпуск блога проверен 18.09.2026.
Редакционные подборки реализованы и проверены локально: список, страницы, живые ссылки
на доступные оригиналы и SEO. [Процесс наполнения](11-collections.md) — файловый;
первые реальные курсы ещё нужно отобрать, выпуск на сервер не выполнен.
Следующие технические срезы — производительность и постмодерация.

E6B реализован отдельным приоритетом до завершения E6A: редактор структуры и теории,
чтение с оглавлением и переходом к тренировке, независимое копирование курса или статьи
вместе с карточками и изображениями. Копия статьи становится приватным курсом.
Права владельцев, идемпотентность, защита от устаревших правок и интерфейсы проверены.
Сохранения со связью с оригиналом и ручным принятием обновлений остаются в E6A.

**Цель:** заработал главный канал роста.

**Задачи**

_Бэкенд_

1. Публикация набора: slug, проверки качества, `moderation_status`, переход в публичный индекс.
2. Meilisearch: схема индекса, синхронизация при изменениях (фоновая задача + периодическая сверка), русская морфология, опечатки, фасеты (предмет, язык, размер, наличие медиа), ранжирование с учётом популярности.
3. Публичные API: каталог, поиск, страница набора, профиль автора; агрессивный кэш в Redis.
4. Счётчики просмотров и копирований (буферизация в Redis, сброс в БД пачками).

## E12. Бета и запуск — 1.5 недели

**Решение:** сид-библиотека переносится на после запуска (см. E13). На старте каталог наполняют сами пользователи, а канал перетока — импорт-мастер с Quizlet и Anki.

**Что это означает.** Органический трафик начнёт расти на 3–4 месяца позже, чем мог бы: пустые страницы каталога индексировать нечего. Значит, первые пользователи придут только из ручных каналов, и к ним нужно готовиться всерьёз — это задачи 6–7 ниже. Соответственно и решение о платных тарифах (E9) окупится не сразу: первые месяцы платящих будет мало просто из-за малого трафика.

**Задачи**

1. Минимальный демонстрационный контент: 15–25 наборов, чтобы каталог и поиск не выглядели сломанными, а на лендинге было что показать в демо-карточке. Только самостоятельно составленные или свободные материалы.
2. Проверка сценария пустого каталога: поиск без результатов, категория без наборов, главная у нового пользователя — везде осмысленные пустые состояния с призывом создать или импортировать набор.
3. Закрытая бета: 30–50 человек (в том числе 3–5 преподавателей с реальными классами), сбор обратной связи, форма отчёта об ошибке внутри продукта.
4. Обработка беты: приоритизация правок, исправление блокеров и заметных шероховатостей.
5. Полировка: тексты интерфейса, пустые состояния, письма, страницы ошибок, favicon, OG-картинки, адаптив на реальных телефонах.
6. Справочный центр: 15–20 статей по частым вопросам, включая «как перенести наборы из Quizlet».
7. Подготовка запуска: посты в тематических сообществах, работа с преподавательскими чатами, Хабр/VC, Telegram-каналы про учёбу и языки.
8. Мониторинг первых дней, дежурство по инцидентам.

**DoD**

- Бета-тестеры прошли полный сценарий без блокеров, средняя оценка удобства собрана.
- Импорт с Quizlet проходит человек, который видит продукт впервые, без обращения в поддержку.
- Пустой каталог не выглядит поломкой ни на одном экране.
- Продукт открыт публично.

0. **Сид-библиотека, 300–500 наборов** (перенесено из E12, работа фоновая и растянутая). Пока её нет, SEO-канал из E6 работает вхолостую, поэтому это первый кандидат сразу после стабилизации запуска:

     Дешёвая альтернатива, которую стоит попробовать первой: конкурс среди первых пользователей и преподавателей за создание качественных публичных наборов.
1. **PWA и офлайн** (2–3 нед). Service Worker, IndexedDB, синхронизация очереди ответов. Закрывает сценарий «учу в метро» — самый частый запрос у школьников.
2. **Мобильные приложения** (8–12 нед). React Native, переиспользование `packages/core`. Даёт пуши, виджеты и канал из магазинов приложений.
   Обновление: по решению владельца мобильный клиент делается отдельным треком параллельно
   (не после запуска) на **Flutter**, offline-first, Android/APK в v1; `packages/core`
   портируется на Dart. План и контекст — [12-mobile.md](12-mobile.md), изменения бэкенда — в `TODO.md`.
3. **ИИ-слой** (4–6 нед). Генерация карточек из вставленного текста и PDF, объяснение ошибок, проверка свободных ответов, распознавание фото учебника. Считать себестоимость на пользователя до запуска; ставить в платный тариф.
4. **Игровые режимы** (2–3 нед). Подбор пар на время, «гравитация», командные режимы. Вирусность у школьной аудитории.
5. **Live-режим для класса** (3–4 нед). WebSocket, соревнование в реальном времени, аналог Kahoot. Сильный аргумент для преподавателей.
6. **Мини-тренировка в Telegram-боте** (1.5 нед). Уникальный канал удержания для рынка СНГ.
7. **Переоптимизация FSRS на своих данных** (2 нед). Когда накопится 1–2 млн записей в `reviews` — подбор персональных параметров. Прямое улучшение главной метрики и хороший инфоповод.

9. **Локализация** на английский и языки СНГ, если появится спрос за пределами РФ.

## Что делать в первую очередь

Ближайшие шаги, если начинать сегодня:

1. Утвердить документы, при необходимости поправить числа лимитов в [04-limits.md](04-limits.md).
2. Зарегистрировать домен, подать заявки на приложения VK ID и Яндекс ID (там модерация, она идёт параллельно разработке).
