# Remora — лимиты и границы тарифов

Документ описывает, где именно проходит граница между бесплатным и платным. Все числа собраны в одном месте намеренно: это конфигурация, а не архитектура, и она будет меняться по данным.

## 1. Принципы

**Принцип 1. Выучить всё, что ты создал сам, можно бесплатно и без ограничений.**
Ни один режим обучения не заблокирован. Нет дневного лимита повторений, нет «вы прошли 5 сессий, приходите завтра», нет рекламы. Это контракт с пользователем и основа позиционирования против Quizlet.

**Принцип 2. Платим за объём, автоматизацию, аналитику и власть над чужим прогрессом.**
Это те четыре вещи, где ценность растёт с серьёзностью намерений пользователя, а вместе с ней растёт и готовность платить.

**Принцип 3. Лимит останавливает создание нового, но не отнимает созданное.**
Превысил квоту изображений — новые не грузятся, старые продолжают работать. Кончилась подписка — все наборы остаются доступными и изучаемыми, отключаются только платные удобства. Никакого «ваши данные заперты, заплатите».

**Принцип 4. Момент оплаты должен совпадать с пиком ценности, а не с пиком раздражения.**
Поэтому платными сделаны «Подготовка к экзамену» (человек в стрессе перед датой, готов платить) и отчёты преподавателя (человек экономит вечер проверки), а не «третий набор» (человек ещё ничего не получил).

**Принцип 5. Экспорт бесплатен всегда.**
Забрать свои данные можно в любой момент на любом тарифе. Это ровно то, чем мы отстраиваемся, и на этом нельзя экономить.

## 3. Контракт: что мы не будем лимитировать никогда

Список публикуется на странице тарифов и в справке. Нарушение любого пункта — изменение позиционирования, а не продуктовая правка.

1. Число повторений и время занятий в день.
2. Доступ к любому режиму обучения.
3. Работу FSRS-планировщика.
4. Возможность выучить уже созданный или скопированный набор.
5. Экспорт своих данных.
6. Доступ к своим наборам после окончания подписки.
7. Показ рекламы.

## 4. Реализация

### 4.1 Два типа ограничений

**Квоты состояния** (`limit`) — проверяются по текущему состоянию базы: число наборов, карточек, изображений, классов. Не требуют счётчиков, считаются запросом с кэшем в Redis на 60 секунд.

**Счётчики использования** (`usage_counters`) — накапливаются за период и сбрасываются: символы TTS в месяц, импорты в сутки, копирования в сутки, экспорты аккаунта в сутки.

```
usage_counters(user_id, metric, period_key, value, updated_at)
  period_key: '2026-09' для месячных, '2026-09-08' для суточных
  PK: (user_id, metric, period_key)
  Инкремент атомарный, через INSERT ... ON CONFLICT DO UPDATE
```

Сброс не нужен: новый период — новый ключ. Старые строки чистятся раз в месяц фоновой задачей.

### 4.2 Единая точка проверки

Никаких `if user.plan == 'plus'` по коду. Всё через один сервис:

```python
class Entitlements:
    def feature(user, key: str) -> bool           # доступна ли фича
    def limit(user, key: str) -> int | None       # значение лимита, None = ∞
    def check(user, key: str, requested: int = 1) # бросает LimitExceeded
    def consume(user, metric: str, amount: int)   # атомарный инкремент счётчика
```

Значения берутся из `plans.features` (jsonb) с наложением персональных `entitlements` (промо, ручная выдача, бонусы за приглашение). Порядок разрешения: персональный override → тариф → дефолт бесплатного.

Конфигурация лимитов живёт в одном YAML, из которого сидируется таблица `plans`, чтобы менять числа без правок кода:

```yaml
free:
  sets.max: 50
  cards.per_set: 300
  cards.total: 3000
  images.total: 60
  tts.chars_per_month: 5000
  classes.max: 1
  ...
```

### 4.3 Точки проверки

| Действие                                       | Проверка                                 |
| ---------------------------------------------- | ---------------------------------------- |
| Создание набора, копирование публичного        | `sets.max`, `cards.total`                |
| Добавление карточек (в т.ч. батчем и импортом) | `cards.per_set`, `cards.total`           |
| Запрос presigned URL на изображение            | `images.total`, `images.max_size`        |
| Вызов синтеза TTS (только при промахе кэша)    | `tts.chars_per_month` → `consume`        |
| Старт импорта                                  | `import.per_day`, `import.cards_per_run` |
| Создание класса, вступление ученика            | `classes.max`, `classes.students_max`    |
| Создание задания                               | `assignments.active_max`                 |
| Запуск теста                                   | `test.questions_max`                     |
| Открытие платного отчёта или графика           | `feature(...)`                           |

Проверка выполняется **на сервере всегда**, на клиенте — дополнительно, ради предупреждения до начала действия. Клиент получает текущие лимиты и остатки в `/api/v1/users/me` и обновляет их после операций, влияющих на счётчики.

### 4.4 Формат ошибки

```json
{
  "code": "LIMIT_EXCEEDED",
  "message": "Достигнут лимит изображений на бесплатном тарифе",
  "details": {
    "limit_key": "images.total",
    "limit": 60,
    "current": 60,
    "requested": 1,
    "resets_at": null,
    "upgrade_to": "plus"
  }
}
```

Для счётчиков с периодом заполняется `resets_at`. Клиент по `limit_key` показывает нужный экран, не разбирая текст сообщения.

### 4.5 Массовые операции

Импорт и батчевое добавление карточек проверяют лимит **до начала работы** и пишут ровно столько, сколько влезает, если пользователь согласился на частичный импорт. Молча обрезать нельзя: в отчёте импорта явно указывается, сколько карточек не добавлено и почему.

## 5. Поведение при превышении

**Тон.** Лимит — не наказание и не ловушка. Сообщение объясняет, что произошло, сколько осталось, когда сбросится и что можно сделать бесплатно.

Плохо: «Обновитесь до Plus, чтобы продолжить».
Хорошо: «В наборе 300 карточек — это максимум для бесплатного тарифа. Можно разбить набор на два (учиться можно будет обоими сразу на Plus) или снять ограничение за 249 ₽/мес».

**Предупреждение заранее.** При достижении 80% квоты — ненавязчивая плашка в интерфейсе, без модальных окон посреди работы. Перед началом импорта, который не влезет, — предупреждение до старта, а не ошибка после.

**Никогда не прерываем сессию обучения.** Если лимит уперся во время тренировки (например, TTS), режим продолжает работать без озвучки, с пометкой. Экран оплаты посреди повторений не появляется никогда.

**Мягкая деградация при окончании подписки:**

- всё созданное остаётся доступным и изучаемым;
- новые действия сверх бесплатных лимитов блокируются;
- превышающий объём не удаляется и не скрывается — например, при 500 изображениях просто нельзя загрузить 501-е;
- настройки FSRS откатываются к значениям по умолчанию, но состояния карточек сохраняются полностью;
- второй и последующие классы переходят в режим «только чтение»: преподаватель видит их и учеников, но не создаёт новые задания.

**Grandfathering.** Контент, созданный до введения или ужесточения лимита, никогда не блокируется. При изменении чисел в конфигурации фиксируется дата, и для затронутых пользователей применяется старый лимит до первого апгрейда. Иначе изменение лимита ломает доверие сильнее, чем приносит выручки.

## 6. Антиабуз

Лимиты бессмысленны, если их обходят вторым аккаунтом. Минимальный набор мер:

- Ограничение числа аккаунтов на один email-домен/IP при аномальной скорости регистраций.
- Подтверждение email обязательно для публикации, импорта больше 200 карточек и создания класса.
- Квоты TTS и импорта привязаны к аккаунту с подтверждённой почтой; неподтверждённые получают 20% от бесплатной квоты.
- Rate limiting на все батчевые эндпоинты.
- Детекция накрутки XP: понижающий коэффициент внутри дня, аномально короткое время ответа не засчитывается.
- Мониторинг топ-потребителей квот раз в неделю: если кто-то нашёл дыру, это будет видно в первой десятке.

Массовое клонирование аккаунтов ради обхода лимитов на нашем масштабе — не главная угроза. Не строить сложную систему до появления реальной проблемы.

## 7. Экономика бесплатного пользователя

Грубая оценка себестоимости активного бесплатного пользователя в месяц. Числа по внешним сервисам требуют сверки с актуальными прайсами перед этапом E9.

| Статья                                                                                          | Оценка         |
| ----------------------------------------------------------------------------------------------- | -------------- |
| Хранение: 60 изображений × ~250 КБ после конвертации ≈ 15 МБ                                    | копейки        |
| Трафик CDN на отдачу медиа                                                                      | единицы рублей |
| TTS: 5 000 символов при высокой доле попаданий в общий кэш → реально 500–1 500 символов синтеза | единицы рублей |
| БД и вычисления: ~1 500 повторений в месяц, дешёвые запросы                                     | копейки        |
| Почтовые уведомления: ~20 писем                                                                 | копейки        |

Итог — единицы рублей на активного бесплатного пользователя. Это принципиально: при отсутствии ИИ в MVP бесплатный тариф не создаёт значимых переменных издержек, и щедрость безопасна. Главные затраты — фиксированные (сервер, домены, время разработчика), и они не растут линейно с числом бесплатных пользователей.

Точка контроля: если средняя себестоимость бесплатного пользователя превысит **15 ₽/мес**, надо ужесточать TTS-квоту, а не всё остальное — именно она единственная статья с реальным риском роста.

---

## 8. Что тюнить по данным после запуска

Лимиты — гипотеза. Что смотреть в первые три месяца:

1. **Доля пользователей, упирающихся в каждый лимит.** Если в лимит наборов упирается меньше 2% активных — он не работает как драйвер оплаты и его надо снижать. Если больше 25% — он раздражает и его надо повышать.
2. **Какой лимит чаще всего предшествует оплате.** Это и есть настоящий продающий лимит, остальные — фон. Ожидание: изображения и отчёты преподавателя. Проверить, а не поверить.
3. **Отвал после экрана лимита.** Если после сообщения о лимите пользователь не возвращается в течение 7 дней — формулировка или сам лимит поставлены неверно.
4. **Средний расход TTS.** Если попадание в общий кэш выше 90%, квоту можно поднять втрое без роста затрат и получить дешёвый маркетинговый аргумент.
5. **Конверсия преподавателей во второй класс.** Если преподаватели не заводят второй класс — лимит выбран не в том месте, крючком должны стать отчёты.

Все числа лежат в одном YAML именно для того, чтобы такие правки занимали минуты, а не релиз.
