# Remora — мобильное приложение (Flutter)

План и технический контекст мобильного клиента. Этот файл — «отдельный план» мобильной
разработки; операционные задачи и изменения бэкенда ведутся в корневом [`TODO.md`](../TODO.md),
как и по всему проекту. При расхождении верить `TODO.md` и коду.

## 0. Статус и связь с общим планом

- **Решение принято на этапе E6A** (до публичного запуска). Мобильное приложение делается
  **отдельным треком параллельно** основной разработке, без жёсткого дедлайна.
- **Отклонение от роадмапа зафиксировано осознанно.** В [`03-roadmap.md`](03-roadmap.md)
  мобильные приложения стояли в E13+ как React Native после запуска. Теперь: **Flutter**,
  **offline-first**, **Android/APK в v1**, старт параллельно, а не после запуска. Причина
  смены стека: единственное преимущество RN — переиспользование `packages/core` на TS —
  отпадает, потому что ради офлайна доменное ядро всё равно портируется на Dart (раздел 7).
- **Backend-изменения** для мобильного собраны в `TODO.md` (сводка — раздел 16 ниже).

## 1. Цель и принципы

**Зачем нужно нативное приложение, а не только мобильный веб/PWA:** офлайн-обучение
(«учу в метро» — самый частый сценарий у школьников и студентов), быстрый локальный отклик
движка обучения без сетевого раунд-трипа, задел под пуши и виджеты в будущем.

Мобильный клиент наследует непреложные правила платформы Remora:

1. **Обучение не лимитируется тарифом.** Ни один режим, ни число повторений, ни доступ к своим
   наборам не зависят от плана. См. раздел 3 в [`04-limits.md`](04-limits.md). В приложении
   не появляется экранов оплаты посреди обучения.
2. **Ответы пользователя нельзя терять.** Отправка ответов — батчами, идемпотентно по
   `client_review_id`, с локальной очередью при обрыве сети. На мобильном это ядро, а не опция.
3. **Один контракт проверки ответов — теперь на три языка.** `app/core/answers.py` ↔
   `packages/core/src/answers.ts` ↔ Dart-порт обязаны вести себя одинаково; их сверяет общий
   `packages/core/src/answer-cases.json` (раздел 7).
4. **FSRS трогать осторожно.** Dart-порт предпросмотра интервалов обязан совпадать с сервером
   до миллисекунды по общим фикстурам; параметры подписаны `SCHEDULER_VERSION`
   (`app/services/scheduler.py`).
5. **Схема API коммитится.** Dart-клиент генерируется из той же OpenAPI-схемы и коммитится;
   CI проверяет актуальность (раздел 8).
6. **Ошибки API — по `code` и `details`,** а не по тексту (`app/core/errors.py`).
7. **Тёмная тема обязательна,** цвета — только через токены (раздел 10), доступность —
   цели нажатия от 44 px, видимый фокус, учёт `prefers-reduced-motion`.
8. **Тексты интерфейса — на русском.** Строки выносятся в i18n с первого дня; вторая локаль — потом.

## 2. Область v1

**Платформа:** Android. **Дистрибуция:** прямой APK со страницы загрузки на сайте
(без Google Play/RuStore на старте). Работа без Google-сервисов не требуется в v1, но
архитектура не должна на них завязываться жёстко (пуши и прочее — потом).

| Входит в v1 | Не входит (потом) |
| --- | --- |
| Вход/регистрация по email+паролю (мобильный auth-flow) | Соцвход (VK ID, Яндекс ID, Telegram) |
| Моя библиотека: свои и сохранённые наборы, поиск по своему | Публичный каталог, поиск и витрина чужих курсов |
| Скачивание наборов для офлайна (карточки + изображения) | Скачивание TTS-аудио (появится с «Аудированием») |
| Обучение офлайн: «Карточки», «Заучивание», «Письмо» | «Аудирование» — с появлением аудио/TTS |
| «Тест» (в v1 онлайн; офлайн — быстрым следующим шагом) | Редактирование наборов/карточек |
| Чтение теории своих/сохранённых курсов (офлайн для скачанных) | Импорт (текст/CSV/Anki) |
| Настройки «Заучивания» (пресеты, упражнения, 1–5, проверка, % совпадения) | Классы и задания (B2B) |
| Экран результатов сессии и статистика набора | Оплата/подписка (только в вебе; в приложении не показываем) |
| Синхронизация ответов (батчи, идемпотентность, локальная очередь) | Пуши и напоминания |
| Тёмная/светлая/системная тема | Транскрипция аудио/видео — вне мобильного вовсе |
| Форс-апдейт (минимальная версия), Sentry | iOS, Google-сервисы, RuStore |

**Офлайн-матрица режимов v1** (честно, без тихих ограничений):

| Режим | Офлайн на скачанном наборе | Комментарий |
| --- | --- | --- |
| Карточки | да | Просмотр, переворот, опциональная запись в FSRS |
| Заучивание | да | Оркестрация раундов и типов упражнений — локально (Dart), см. раздел 7/11 |
| Письмо | да | Нормализация и сравнение — локально по общему контракту |
| Тест | **онлайн в v1** | Сервер фиксирует вопросы в `test_attempts`; офлайн-тест — быстрый следующий шаг, требует небольшого контракта на приём клиентски сгенерированной попытки |
| Аудирование | нет (в v1 отсутствует) | Нужны аудиоплеер и TTS-ключ Яндекс SpeechKit (сейчас не заведён) |

## 3. Технические решения (стек)

**Flutter** (Dart). Обоснование выбора против альтернатив — раздел 0.

| Область | Выбор | Роль / обоснование |
| --- | --- | --- |
| Сеть | `dio` + интерсепторы | single-flight refresh, повторы, единая обработка ошибок по `code` |
| API-клиент | `openapi-generator` (flavor `dart-dio`) | генерация из OpenAPI, ложится на `dio` (раздел 8) |
| Локальная БД / офлайн | **Drift** (SQLite) | типизированный, async; реляционная модель совпадает со схемой сервера (раздел 6) |
| Состояние | **Riverpod** | ближайший аналог связки TanStack Query + Zustand из веба |
| Навигация | `go_router` | декларативные маршруты, deep links под будущее |
| Секреты | `flutter_secure_storage` | refresh-токен в Keychain/Keystore |
| Формулы | `flutter_math_fork` | LaTeX; «похоже», не идентично KaTeX (принято) |
| Код | `flutter_highlight` | подсветка; темы приближают Shiki, не совпадают точно |
| Markdown | `markdown` + кастомный рендер | строго whitelist под серверную санитизацию |
| Изображения | `cached_network_image` + файловый кэш | офлайн-кэш скачанных наборов |
| Знак | `flutter_svg` из `remora-mark.svg` | без перекраски и перерисовки (раздел 10) |
| Ошибки/аналитика | `sentry_flutter` | тот же Sentry, что у API и вебов |

**Минимальные версии ОС (выбор):** Android 7.0 (minSdk 24) — покрывает почти весь парк РФ/СНГ
и совместим с `flutter_secure_storage`; targetSdk — актуальный. Для будущего iOS — 13+.

## 4. Архитектура приложения

Offline-first, слоями, source of truth — сервер, на устройстве — зеркало.

```
        UI (виджеты, экраны)  ── Riverpod providers ──┐
                                                       │  читает локально мгновенно
        domain (Dart-порт ядра: answers, fsrs,         │  пишет в outbox
                distractors, learn state machine)      │
                                                       ▼
        data (repositories: SetRepo, StudyRepo, …) ─── источники:
                                                       ├─ ApiClient (dio, сгенерирован)
                                                       ├─ Local DB (Drift)
                                                       ├─ SecureStorage (токены)
                                                       └─ FileCache (медиа)
```

**Принцип чтения:** экраны читают из локальной БД (быстро, работает офлайн), фоновая
синхронизация обновляет её из API. **Принцип записи:** мутации (ответы) пишутся в локальный
outbox и отправляются батчами; сервер остаётся источником истины и пересчитывает состояние.

Состояния данных каждого экрана проектируются по [`design.md`](../design.md): загрузка, пусто,
данные, частичная ошибка, полная ошибка, потеря сети, повторная синхронизация, нет прав, лимит.

## 5. Аутентификация (мобильный flow)

**Сейчас (браузер):** access-JWT (15 мин) живёт в памяти SPA, refresh-токен — в `httpOnly`
Secure cookie с путём `/api/v1/auth`, ротация с детекцией переиспользования семьи токенов
([`apps/api/app/api/v1/auth.py`](../apps/api/app/api/v1/auth.py)). Для нативного клиента cookie
не подходят.

**Мобильный flow:**

- access-JWT — в памяти приложения; refresh-токен — в `flutter_secure_storage`.
- При `login`/`register` с мобильного клиента сервер возвращает refresh **в теле** ответа
  (в дополнение к cookie для веба). Признак мобильного — заголовок (например, `X-Client: mobile`).
- `POST /auth/refresh` принимает refresh из заголовка/тела, когда cookie отсутствует.
- **Ротация и детекция переиспользования семьи токенов сохраняются без изменений** — та же
  таблица `refresh_tokens`, тот же механизм отзыва семьи. В `user_agent`/устройство пишем
  имя устройства для списка сессий.
- Интерсептор `dio`: при 401 — single-flight refresh (десять параллельных 401 не должны
  запускать десять refresh), затем повтор исходного запроса; тело POST/PUT сохраняется.
- **PAT (`api_tokens.py`) не используется** — он намеренно не даёт доступа к аккаунту.

Изменения на бэкенде — раздел 16 и `TODO.md`.

## 6. Офлайн и синхронизация

**Локальная БД (Drift), зеркало серверных сущностей + служебные таблицы:**

- `sets`, `cards` — метаданные и содержимое скачанных наборов (термин, определение,
  транскрипции, `content_type`, `code_language`, `alt_answers`, неверные ответы обоих
  направлений, ссылки на медиа).
- `card_states` — состояние FSRS по паре (карточка, направление) для скачанных наборов:
  `state`, `stability`, `difficulty`, `due_at`, `reps`, `lapses` и т.д. Раздельно по направлению.
- `study_sessions` — локальный курсор активной сессии (совместим с серверной `StudySession`).
- `review_outbox` — очередь неотправленных ответов: `client_review_id` (UUID),
  `card_id`, `direction`, `rating`, `answer_correct`, `mode`, `duration_ms`, `reviewed_at`,
  `session_id`, статус отправки, число попыток. **Никогда не очищается до подтверждения сервером.**
- `courses`, `sections`, `articles` — структура и безопасный текст теории скачанных курсов.
- `media_cache` — соответствие `s3_key`/URL → локальный файл (изображения; аудио позже).
- `sync_meta` — курсоры/ревизии для инкрементальной подтяжки, время последней синхронизации.
- `settings_cache` — общие и заданные для набора настройки «Заучивания», чтобы режимы
  работали офлайн.

**Скачивание набора:** по кнопке «Сделать доступным офлайн» — карточки + изображения
(и TTS-аудио, когда появится) складываются в БД и файловый кэш. Рассмотреть серверный
«bundle»-эндпоинт (карточки + состояния + ссылки на медиа одним запросом) как оптимизацию;
в v1 допустимо переиспользовать существующие эндпоинты `sets`, `study`, `media`.

**Цикл обучения офлайн:** очередь FSRS собирается локально (просроченные + новые в пределах
дневного лимита), следующий шаг вычисляется Dart-портом мгновенно; каждый ответ пишется в
`review_outbox`.

**Синхронизация:** при появлении сети outbox отправляется в
`POST /study/sessions/{id}/answers` (батч, идемпотентно по `client_review_id`), затем
подтягиваются актуальные состояния. Сервер — источник истины: при расхождении перезаписываем
локальные состояния серверными. Ревизии наборов/курсов сверяются, чтобы не учить по устаревшему
содержимому. Конфликтов данных быть не должно: клиент только добавляет иммутабельные ответы,
пересчёт — на сервере.

**Что офлайн в v1:** обучение по скачанным наборам («Карточки», «Заучивание», «Письмо»),
чтение теории скачанных курсов, просмотр своей библиотеки. Онлайн: вход, скачивание,
синхронизация, «Тест» (см. матрицу в разделе 2).

## 7. Переиспользование доменного ядра (Dart-порт)

Ради офлайна логика из `packages/core` портируется на Dart. Живёт отдельным пакетом внутри
мобильного репозитория.

**Портируется и покрывается тестами против общих кейсов:**

- `answers.ts` → нормализация и сравнение ответов; сверка по
  [`packages/core/src/answer-cases.json`](../packages/core/src/answer-cases.json).
- `fsrs.ts` → предпросмотр интервалов; сверка по
  [`packages/core/src/fsrs-cases.json`](../packages/core/src/fsrs-cases.json). **Совпадение
  с сервером до миллисекунды.** При изменении планировщика поднимается `SCHEDULER_VERSION`
  и перегенерируются фикстуры (`scripts/gen_fsrs_fixtures.py`), затем обновляется Dart-порт.
- `distractors.ts` → варианты ответа для «Заучивания» и «Теста».
- `format.ts` → форматирование.
- `card-import.ts` — **не портируется в v1** (импорт отложен).

**Важно — не всё ядро лежит в `packages/core`.** Оркестрация «Заучивания» (раунды 7–10 карточек,
прогрессия типов упражнений по стабильности, цель 1–5 успехов, возврат карточки в конец очереди,
разбор ошибки) на вебе живёт в `apps/app` (Zustand), а не в общем пакете. Для мобильного эту
машину состояний нужно **реализовать на Dart заново** по контракту из
[`02-functional-spec.md`](02-functional-spec.md) (4.3) и [`08-bots.md`](08-bots.md). Это
отдельный объём, не покрытый существующими файлами ядра.

Правило трёх языков фиксируется в CI мобильного репозитория: тесты Dart-порта гоняются на тех же
`answer-cases.json` и `fsrs-cases.json`.

## 8. Генерация API-клиента

- **Источник схемы** — тот же, что у веба: `apps/api/scripts/dump_openapi.py` формирует
  `apps/api/openapi.json` (запущенный сервер не нужен, генерация воспроизводима; см.
  [`scripts/gen-api-client.mjs`](../scripts/gen-api-client.mjs)).
- **Инструмент (установлен).** `@openapitools/openapi-generator-cli` — dev-зависимость в корне
  монорепо; версия генератора закреплена в [`openapitools.json`](../openapitools.json) — **7.25.0**.
  Flavor `dart-dio` → Dart-клиент, коммитится в мобильный репозиторий (иначе чистый клон не
  собирается). Сам JAR лежит в `node_modules` (в git не попадает). Проверено на
  `apps/api/openapi.json`: 128 моделей, 19 API-классов, есть готовый `bearer_auth` под
  мобильный токен-flow (раздел 5).
- **CI мобильного** проверяет актуальность сгенерированного клиента (зеркало проверки
  `pnpm gen:api` в основном репозитории).
- **Доступ сабмодуля к схеме:** так как схема живёт в основном репозитории, нужно решить, как
  мобильный репозиторий получает `openapi.json` — держать его закоммиченным в `apps/api` и
  читать через родительский репозиторий, либо в мобильном репозитории вызывать `dump_openapi.py`.
  Решение зафиксировать при заведении репозитория (раздел 17).
- После правок мобильного auth на бэкенде — `pnpm gen:api` и коммит
  `packages/api-client/src/generated/schema.ts` (CI это проверяет).

## 9. Рендеринг содержимого карточек

Паритет «похоже, не идентично» (принято владельцем):

- **Markdown** — ограниченный сабсет строго под серверную санитизацию (жирный, курсив,
  подчёркивание, переносы, списки, inline-код, блоки кода). HTML не исполняется, внешние
  ресурсы не загружаются — как в общем безопасном рендерере веба.
- **LaTeX** — `flutter_math_fork` (инлайн `$…$` и блочные `$$…$$`); допускается горизонтальная
  прокрутка формул.
- **Код** — `flutter_highlight`, моноширинный шрифт, сохранение отступов и переносов.
- **Изображения** — `cached_network_image` + офлайн-файлы; по умолчанию `object-contain`-поведение.
- Текст учебной карточки центрируется и масштабируется в шкале `card-sm`–`card-lg`.

**Бренд.** Знак — из [`remora-mark.svg`](../packages/ui/src/assets/remora-mark.svg) через
`flutter_svg`, **без перекраски, перерисовки и градиентов**. Цвета знака фиксированы:
`#0D8285`, `#FFFFFF`, `#EA8D2F`. Минимальный размер — 32 × 32 px. Растровые иконки приложения
(launcher) экспортируются из мастер-SVG.

**Типографика:** Inter → system; код — JetBrains Mono → monospace. Основной текст 16 px,
пояснения 14 px, содержимое учебной карточки 24–44 px.

**Пространство и форма:** базовый шаг 4 px; радиусы полей/кнопок 10–14 px, крупных карточек
14–24 px; тени отделяют интерактивные карточки, но не заменяют границу.

**Доступность и движение:** цели нажатия ≥ 44 px, видимый фокус (общий `primary` outline),
короткие анимации 120–180 мс, при `prefers-reduced-motion` движение практически отключается.
Ответ сначала сохраняется локально, состояние синхронизации видно и не блокирует обучение.

## 11. Режимы обучения

Общая оболочка тренировки (очередь, прогресс, восстановление сессии, outbox с ретраями,
горячие действия) + режимы поверх неё. Настройки «Заучивания» — общие профиля и переопределения
для набора (пресеты «Быстро»/«Обычно»/«Тщательно», включённые упражнения, 1–5 успехов, способ
проверки, порог посимвольного совпадения), тот же контракт, что в вебе и ботах
([`08-bots.md`](08-bots.md)).

- **Карточки** — переворот, навигация, свайпы, перемешивание, фильтры; опциональная запись в FSRS.
- **Заучивание** — раунды, прогрессия типов упражнений, самооценка/автопроверка, разбор ошибки
  с подсветкой различий (машина состояний портируется на Dart, раздел 7).
- **Письмо** — ввод текста, нечёткое сравнение по общему контракту, статус «опечатка».
- **Тест** — в v1 онлайн (сервер фиксирует вопросы); разбор и пересдача по ошибкам.
- **Аудирование** — с появлением аудиоплеера и TTS-ключа; деградация до текста при недоступном TTS.

Экран результатов сессии и статистика набора (процент освоения, распределение состояний,
проблемные карточки) — по [`02-functional-spec.md`](02-functional-spec.md) (4.3).

**Используемые эндпоинты:** `study/{set_id}/queue`, `study/{set_id}/session`,
`study/sessions/{id}/answers` (batch), `study/sessions/{id}/finish`, `study/due-today`,
`study/forecast`; библиотека и наборы — `users/me`, `sets/*`, `library/*`; чтение курсов —
`courses/*`.

## 12. Уведомления, обновление, наблюдаемость

- **Пуши — потом.** В v1 отсутствуют. При добавлении учесть устройства без Google-сервисов
  (возможны несколько транспортов: FCM, RuStore Push, APNs) и завязку на очередь уведомлений E7.
- **Форс-апдейт (в v1).** Прямой APK не обновляется автоматически, поэтому приложение при старте
  спрашивает у бэкенда минимально поддерживаемую версию и при устаревании показывает экран
  «обновите приложение» со ссылкой на APK.
- **Наблюдаемость.** `sentry_flutter` для ошибок и крэшей; технические детали пользователю
  не показываются (голос интерфейса — [`design.md`](../design.md)).

## 13. Репозиторий, структура, CI

- **Отдельный git-репозиторий**, подключён как **submodule** в `apps/mobile` основного репозитория.
  Предлагаемое имя репозитория — `remora-mobile`, bundle id — `ru.eduremora.app` (оба —
  на подтверждение, раздел 17). Основной репозиторий пинит коммит мобильного.
- **Структура каталогов** (ориентир):

```
remora-mobile/
├── lib/
│   ├── app/            точка входа, тема (из токенов), роутинг (go_router)
│   ├── core/           Dart-порт ядра: answers, fsrs, distractors, format
│   ├── data/           Drift-схема, репозитории, ApiClient (сгенерирован), secure storage
│   ├── features/       auth, library, study (режимы), courses (чтение теории), settings
│   └── shared/         рендер контента, общие виджеты, состояния данных
├── test/               тесты, включая сверку с answer-cases.json / fsrs-cases.json
└── ci/                 конфиг CI: analyze, test, build apk, проверка клиента и порта
```

- **CI мобильного (в его репозитории):** `flutter analyze`, `flutter test`,
  `flutter build apk`; проверка актуальности сгенерированного Dart-клиента и Dart-порта ядра
  против общих кейсов.

## 14. Тестирование

Зеркалит обязательное покрытие проекта (см. [`02-functional-spec.md`](02-functional-spec.md), 7):

- **Нормализация ответов** — Dart-порт против `answer-cases.json`.
- **FSRS** — Dart-порт против `fsrs-cases.json`, совпадение до миллисекунды.
- **Офлайн-очередь** — обрыв сети посреди сессии не теряет ни одного ответа; идемпотентность
  повторной отправки по `client_review_id`.
- **Auth** — жизненный цикл токенов, single-flight refresh, сохранение тела запроса при повторе.
- **Виджет-тесты** ключевых экранов режимов, светлая/тёмная тема, цели нажатия.

## 15. Этапы

Оценки грубые (жёсткого дедлайна нет, трек параллельный). Каждый этап заканчивается
проверяемым состоянием.

- **M0 — Каркас.** Проект, стек, CI, тема из токенов (свет/тьма), знак, экран-заглушка, Sentry.
  *DoD:* приложение собирается в APK, открывается, тема переключается.
- **M1 — Мобильный auth + Dart-клиент.** Backend-правки auth (раздел 16), генерация клиента,
  экраны входа/регистрации, хранение токенов, refresh-интерсептор, защищённые маршруты.
  *DoD:* логин end-to-end на дев-сервере; сессия переживает перезапуск приложения.
- **M2 — Порт ядра на Dart.** `answers` (+ `answer-cases.json`), FSRS-предпросмотр
  (+ `fsrs-cases.json`, до мс), дистракторы, форматирование. *DoD:* оба набора кейсов зелёные в CI.
- **M3 — Библиотека + офлайн-хранилище.** Drift-схема, экран моей библиотеки, поиск по своему,
  скачивание набора (карточки + изображения), pull состояний / push ответов идемпотентно.
  *DoD:* скачал набор → отключил сеть → данные и состояния на месте.
- **M4 — Оболочка обучения.** Локальная очередь FSRS, прогресс, восстановление сессии, outbox
  с ретраями, рендерер контента. *DoD:* обрыв сети посреди сессии не теряет ни одного ответа.
- **M5 — Режимы.** «Карточки», «Заучивание» (машина состояний + настройки), «Письмо»; «Тест»
  онлайн. Экран результатов и статистика набора. *DoD:* набор на 50 карточек проходится офлайн,
  синхронизируется онлайн, интервалы совпадают с сервером.
- **M6 — Чтение теории.** Свои/сохранённые курсы: структура → статьи, безопасный рендер, переход
  к набору; офлайн для скачанных. *DoD:* чтение теории офлайн и переход к обучению.
- **M7 — Аудирование + аудио.** Плеер, офлайн-аудио, режим с деградацией. *Зависит от TTS-ключа
  Яндекс SpeechKit (внешняя задача, сейчас не заведён).*
- **M8 — Полировка и релиз.** Форс-апдейт, пустые состояния всех экранов, тёмная тема, цели
  ≥ 44 px, релизный APK и страница загрузки на сайте.

**Post-v1 backlog:** редактирование наборов/карточек, импорт, публичный каталог/поиск, пуши и
напоминания, соцвход, iOS (нужен Mac + Apple Developer), Google-сервисы/RuStore, отображение
статуса подписки (оплата остаётся в вебе), офлайн-«Тест».
